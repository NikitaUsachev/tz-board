# Версия 28

## Что меняется сразу после публикации сайта

- Независимые правки в разных полях объединяются с проверкой версии записи. Спорные поля и списки требуют явного выбора между показанными вариантами; повторное сохранение также проверяет версию.
- Удаление стало перемещением в корзину: в JSON мероприятия сохраняются deletedAt/deletedBy. Физического удаления строк и вложений через интерфейс нет. Восстановление проверяет версию.
- Черновики сохраняются под почтой администратора в localStorage данного браузера. При нехватке места сайт предупреждает; переход с несохранённым черновиком блокируется, если запись на устройство не удалась.
- При внутреннем переходе из редактора предлагается остаться или сохранить черновик и перейти. Перед закрытием страницы остаётся системное предупреждение.
- Перед сохранением и восстановлением приложение запрашивает свежие мероприятия на ту же дату и предупреждает о пересечении залов.
- Имя техника, общие отметки, назначение залов, вложения и прежние ссылки сохранены.

## Важные границы

Проверка занятости на странице не является атомарной: два запроса могут пройти одновременно. Для гарантии на уровне базы нужен SQL ниже.
До его применения сайт скрывает ТЗ из корзины при чтении, но прежняя серверная функция get_event может по-прежнему вернуть их через прямой запрос. Это НЕ отзыв серверного доступа к удалённому ТЗ.
Черновики не являются резервной копией: очистка браузера удаляет их. Они не синхронизируются с устройствами и коллегами.
Вложения физически сохраняются. Автоматическая очистка не включена: ещё не проверены реальные Storage-политики и ссылки из всех серверных данных и локальных черновиков.

## Следующий шаг в Supabase

1. Выполнить inspect-supabase.sql (только чтение) и проверить определения RLS, RPC, триггера версий и Storage-политик. Полученные определения проверяются отдельно, поскольку их нет в GitHub.
2. Убедиться, что сайт v28 опубликован. Сделать доступную в проекте резервную копию/экспорт данных до изменения схемы. Состояние реальных резервных копий из кода определить нельзя.
3. После проверки применить migrations/20261101_safety.sql в SQL Editor от владельца проекта. Скрипт выполняется в транзакции, при ошибке все его изменения откатываются.
4. Скрипт добавляет приватную историю предыдущих версий ТЗ, ограничение прямого чтения доски, новый метод чтения get_event_v2 без ТЗ из корзины и серверную проверку совпадений залов и дат. Сохраняет аккаунты, SMTP, существующие отметки и Storage-политики. Методы чтения ТЗ и отметок получают дополнительные проверки без изменения сигнатур.
5. Старый метод get_event сохраняется для уже открытых страниц, но исключает ТЗ из корзины. v28 использует get_event_v2; до применения миграции использует прежний метод только при отсутствии нового. Отметки проверяются по выбранным залам и действующим пунктам; для выполнения обязательно имя. Во время записи отметки блокируется параллельное изменение ТЗ.
6. Если диагностика показала уже существующие совпадения залов и дат, проверить их до применения ограничения. Триггер не исправляет исторические совпадения автоматически.
7. Проверить новым и анонимным пользователем запрет чтения списка событий, отсутствие удалённого ТЗ по ссылке, работу отметок, отказ в административных операциях, параллельные сохранения и восстановление.

SQL подготовлен, но не выполнялся на действующей базе и не проверялся PostgreSQL-сервером в локальном окружении. Без определения существующих RPC нельзя считать аудит серверной авторизации завершённым.
История создаёт снимки только последующих изменений; она не заменяет резервную копию всего проекта и файлов.
